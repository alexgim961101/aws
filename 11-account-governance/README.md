# 11. Account Governance — 계정 관리와 거버넌스

## 목표

멀티 계정 구조와 사람·시스템의 자격 증명 수명주기를 설계할 수 있게 된다. 채용공고의 "계정 관리 / 권한 관리" 요구사항을 정면으로 다루는 단계.

## 이론

- [ ] 계정 분리 전략: 왜 prod/dev/보안 계정을 나누는가 — 계정은 가장 강한 격리·과금 경계
- [ ] AWS Organizations: OU 구조 설계, 통합 결제, 조직 단위 서비스 활성화
- [ ] SCP(서비스 제어 정책): 권한을 "주는" 게 아니라 "상한을 긋는" 정책, 대표 패턴(리전 제한, 루트 차단 등)
- [ ] Control Tower / Landing Zone: 개념과 제공 가드레일 (개요 수준)
- [ ] IAM Identity Center(구 AWS SSO): 권한 세트, 계정 할당, 사람의 온보딩·오프보딩 프로세스
- [ ] 크로스 계정 액세스 패턴: AssumeRole 체인, CI/CD용 배포 역할, 감사용 읽기 역할 설계
- [ ] 자격 증명 수명주기: 장기 액세스 키 최소화·로테이션, 임시 자격 증명으로의 전환, 자격 증명 보고서로 점검
- [ ] 조직 수준 감사: 조직 CloudTrail, 중앙 로깅 계정 패턴
- [ ] Well-Architected Framework 총정리: 6개 기둥으로 전체 커리큘럼 복습 — 각 기둥마다 "내가 배운 것" 매핑

## 실습 (labs/)

- Organizations 조직 생성 → 멤버 계정 1개 생성 (이메일 별칭 활용)
- OU 구성 + SCP 적용 (예: 특정 리전 외 사용 차단) → 멤버 계정에서 차단 확인
- IAM Identity Center 활성화 → 권한 세트 만들고 SSO로 멤버 계정 로그인
- 관리 계정 ↔ 멤버 계정 간 AssumeRole 크로스 계정 역할 구성
- 비용: Organizations · SCP · Identity Center 모두 **무료** — 개인 계정으로 안전하게 실습 가능

## 완료 기준

- notes/ 에 이론 정리 작성 (특히 "내가 조직을 설계한다면"의 OU/계정 구조도)
- SSO 로그인과 SCP 차단 동작 확인
- Well-Architected 6개 기둥 총정리 노트 작성 — 커리큘럼 졸업 문서

## 셀프 체크

1. 하나의 계정에서 IAM으로만 격리하는 것과 계정을 나누는 것의 결정적 차이는?
2. SCP가 Allow를 포함해도 권한이 부여되지 않는 이유는? 정책 평가에서 SCP의 위치는?
3. 신규 입사자에게 개별 IAM 유저 대신 Identity Center를 쓰면 온보딩·오프보딩이 어떻게 달라지는가?
4. 감사팀에 모든 계정의 읽기 권한을 주는 구조를 어떻게 설계하는가?
5. 조직에 장기 액세스 키가 몇 개나 살아있는지 어떻게 파악하고 줄여나가는가?
