# 06. Observability — 관측 가능성

## 목표

"장애를 사용자보다 먼저 아는" 상태를 만들기 위해, 앞 단계에서 만든 스택에 로그·메트릭·알람을 붙인다.

## 이론

- [ ] CloudWatch 메트릭: 네임스페이스, 차원, 기본 메트릭 vs 상세 모니터링 vs 커스텀 메트릭
- [ ] CloudWatch Logs: 로그 그룹·스트림, 보존 기간 설정(기본 무제한의 함정), Logs Insights 쿼리
- [ ] 구조화 로깅: JSON 로그를 남겨야 하는 이유, 로그에서 메트릭 추출(metric filter)
- [ ] CloudWatch 알람: 임계값·기간·평가 방법, 복합 알람, SNS 연동(이메일/Slack)
- [ ] 알람 설계론: 무엇을 알람으로 걸어야 하는가 — 증상 기반 vs 원인 기반, 알람 피로 방지
- [ ] CloudTrail: 관리 이벤트 vs 데이터 이벤트, 감사 로그로서의 역할
- [ ] X-Ray 개요: 분산 추적이 필요한 순간
- [ ] 대시보드: 서비스 상태를 한 화면에 — 무엇을 올릴 것인가

## 실습 (labs/)

- 05의 서버리스 스택(또는 04의 ECS 스택)에:
  - 구조화 로그 적용 + 로그 보존 기간 설정
  - 에러율·지연시간 알람 생성 → SNS 이메일 연동
  - Logs Insights로 에러 원인 쿼리
  - 핵심 지표 대시보드 1장 구성
- 의도적으로 에러를 발생시켜 알람 수신까지 확인
